2 · What happens to one Brief

Figure 2 — one Brief through three gates. A failed set stops, its PR becomes a draft, and the trunk is untouched.

What changed, in one line. Every gate now separates done from stuck without a human. Implementation and Tester pass on findings that must name a file and a source doc; Security passes on scanner severity; coverage is a floor that ratchets up. The three self-assigned 0.99 scores are gone, and install.mjs --verify fails the build if one comes back.

5 · What v3 changed

Areav2v3
Stop conditions
new skill		 confidence, code_confidence, ux_confidence each ≥ 0.99 — emitted by the agent that did the work, after reading the threshold specloom-findings. A finding needs a file and a resolvable source or it is dropped. Green = zero critical, zero major
Coverage≥ 0.99 flat coverage_floor default 0.90, ratcheting up on every green Brief. Added ignore directives are audited; one covering AC logic is a major finding
Visualux_confidence ≥ 0.99 per-criterion pass/fail against a named Image File. A failed criterion is a major finding pointing at the component, not the image
BudgetsRetry ≤ 5 for the whole Brief; no spend limit 3 / 2 / 3 per gate, 6 per Brief, plus token_budget_per_brief 250k. Three identical (file, rule) failures stop the gate early
Git undo
new		no way to undo a merged stack revert_stack — reverse merge order, -m 1, never a force-push
Failed run_set"stop the set" — the rest undefined, leaving orphaned PRs failed PR → draft with the stuck gate; earlier green PRs stay open and blocked; worktrees removed; trunk untouched
Linear down"fail if missing" — total halt resolving and planning halt; in-flight work and merges proceed; Done transitions defer to .specloom/pending-linear.json
Language skillsgenerated per run, never stored — two Briefs could build under different rules pinned to .specloom/skills/ and committed. Mounted as-is, never regenerated
UX refsregenerated freely, so acceptance criteria moved between runs draft → frozen after review. A Brief citing a draft reference is not Ready
Skill loadinga bare bullet list per agent — selection was a per-run judgement every agent has a when-to-load table. Same Brief, same rule set
Tracker
new		 Linear only, named directly throughout the contract, queue and resolve-work tracker: linear | github, chosen once at bootstrap and recorded on the Overview. GitHub uses issue types, --parent sub-issues and native --blocked-by. One product, one tracker — never a fallback when one fills up, because a split queue cannot resolve depends_on across the halves

6 · The verifier

node scripts/install.mjs --v3 --verify Fails the build on any of: a **specloom-x** reference that resolves to nothing; a file naming a retired agent; a SKILL.md whose frontmatter name differs from its directory; a surviving Status: STUB; or a reintroduced confidence_score / code_confidence / ux_confidence.

Still worth doing first. v3 is complete as a specification and verified as a package, but no Brief has been run through it end to end. The rules for Implementation, Security and Tester were written from the architecture, not from watching them fail. Run one small real Brief before trusting the defaults — particularly coverage_floor 0.90, the 3/2/3 attempt split, and the 250k ceiling, which are reasoned estimates rather than measurements.
